# 파일럿 지표 계측 — 문의 전환 · 유료 의향 · 지표 화면

작성일: 2026-09-29
상태: 사용자 방향 확정 (2026-09-29 "지표 계측으로 고고")

## 1. 배경

사업계획서(모두의 창업 제출본 2026-09-10) 4단계:

> 5곳 내외의 파트너 중개사무소를 무료로 온보딩해 실제 매물을 등록받고 … 이 단계에서 확인할 지표는
> 등록 매물 수, 급매 알림 신청 수, 매물 문의 전환율, 그리고 중개사의 "유료여도 계속 쓰겠는가"에 대한 답변입니다.

| 지표 | 2026-09-29 현재 |
|---|---|
| 등록 매물 수 | 매물 테이블로 셀 수는 있다. 중개사별·기간별로 보는 화면이 없다 |
| 급매 알림 신청 수 | 있음 (관리자 통계 카드) |
| 매물 문의 전환율 | **잴 수 없다.** 문의는 `tel:`·`mailto:` 링크일 뿐이고 조회도 세지 않는다 |
| 유료 의향 | 없음 |

## 2. 목표

1. 매물 조회와 문의 버튼 누름을 **방문자를 식별하지 않고** 센다.
2. 중개사에게 "유료여도 계속 쓰겠는가"를 제품 안에서 묻고 답을 저장한다.
3. 운영자는 네 지표를 한 화면에서 기간별로 보고 CSV 로 내려받는다(지원사업 보고용).
4. 중개사는 자기 매물의 조회·문의 수를 본다 — 멤버십이 파는 가치("근거를 보고 연락하는 고객과의 연결")를 눈으로 확인하는 자리.

## 3. 비목표

- 방문자 추적: 쿠키, 방문자 식별자, 유입 경로, 체류 시간
- 외부 분석 도구(Google Analytics 등) 도입
- 실제 통화·메일 발송 여부 확인 (버튼을 누른 것까지만 안다)
- 결제·멤버십 (파일럿 다음 단계)

## 4. 무엇을 세는가

| 이름 | 세는 순간 | 중복 처리 |
|---|---|---|
| 조회 `view` | 매물 상세 화면이 열렸을 때 | 같은 브라우저 · 같은 날 · 같은 매물은 1회 |
| 문의 `inquiry_tel` · `inquiry_email` | 전화 또는 이메일 버튼을 눌렀을 때 | 같은 브라우저 · 같은 날 · 같은 매물은 **채널과 상관없이** 1회. 먼저 누른 채널로 기록 |

문의를 채널별로 따로 세지 않는 이유: 한 사람이 전화와 이메일을 둘 다 누르면 문의가 2건이 되어 전환율이 100% 를 넘는다
(로컬 검증에서 200% 가 나와 고쳤다). 문의 수는 "문의한 방문자 수"이고, 전화·이메일 구분은 "처음 쓴 연락 수단"이다.

**세지 않는 것**

- 운영진(admin·owner)의 조회 — 검수하느라 여는 것이다
- 그 매물 담당 중개사 본인의 조회 — 등록 직후 확인하느라 여는 것이다
- 검색 로봇·자동화 브라우저 (User-Agent 와 `navigator.webdriver` 기준)

두 제외 규칙은 브라우저(요청을 아예 보내지 않음)와 DB 함수(로그인 사용자를 다시 확인) 양쪽에서 건다.

**문의 전환율 = 문의 ÷ 조회, 중개사가 등록한 매물만.**
수집 매물(번들 387건)은 담당자가 "급매 운영팀"이고 연락처가 없어 문의 버튼 자체가 없다.
분모에 넣으면 전환율이 의미 없이 낮아진다. 수집 매물의 조회 수는 따로 보여준다.

하루의 경계는 한국 시간이다.

## 5. 개인정보

- 서버로 보내는 것은 **매물 id 와 종류(조회/전화/이메일) 두 가지뿐**이다.
- 저장하는 것은 매물별 **일별 합계**다. 개별 기록(누가·언제)은 저장하지 않는다.
- 중복 제거는 브라우저 안에서만 한다(localStorage `geupmae:tracked`, 날짜가 바뀌면 비운다). 방문자 식별자를 만들지 않는다.
- 설문은 로그인한 중개사 본인의 답이다(계정에 연결). 본인과 운영진만 읽는다.

개인을 식별하는 정보를 수집하지 않으므로 동의 절차는 두지 않는다. 푸터에 집계 사실을 한 줄로 알린다.

## 6. 데이터 모델

마이그레이션 `20260930150000_pilot_metrics.sql`.

### 6.1 `property_daily_stats`

| 열 | 뜻 |
|---|---|
| `property_id` text · `day` date | 기본키 |
| `agent_email` text | 집계 시점의 담당 중개사 계정. 매물이 지워져도 중개사별 합계가 남게 한다. 수집 매물은 null |
| `views` · `inquiry_tel` · `inquiry_email` integer | 그날의 합계 |

매물 테이블에 외래키를 걸지 않는다 — 팔려서 지운 매물의 기록도 파일럿 지표다.
RLS 를 켜고 정책을 만들지 않는다. 읽기·쓰기는 아래 두 함수로만 한다.

### 6.2 함수

| 함수 | 누가 | 하는 일 |
|---|---|---|
| `track_property_event(p_property_id, p_event)` | 누구나(비로그인 포함) | 매물이 실제로 있는지 확인 → 운영진·담당 중개사면 세지 않음 → 그날 합계 +1. 반환: 셌는지 여부 |
| `property_stats(p_from, p_to)` | 로그인 사용자 | 운영진은 전체, 중개사는 자기 매물만, 그 밖은 빈 결과. 매물별 합계와 일별 합계를 jsonb 하나로 반환 |

매물이 실제로 있는지 확인하는 이유: 아무 id 나 받아 주면 행을 무한히 늘릴 수 있다. 확인하면 행 수가 (매물 수 × 날짜 수)로 묶인다.
jsonb 하나로 돌려주는 이유: API 의 1,000행 제한에 걸리지 않게.

### 6.3 `agent_pricing_intents` (유료 의향)

| 열 | 뜻 |
|---|---|
| `user_id` uuid | 기본키 — 중개사 한 명에 답 하나(고치면 덮어씀) |
| `email` text | 답한 계정 |
| `willing` | `yes` 계속 쓰겠다 · `depends` 가격에 따라 · `no` 아니다 |
| `price_band` | 낼 수 있는 월 요금 구간 (`no` 면 비움) |
| `comment` text | 이유·바라는 점 (선택, 500자) |
| `listing_count` integer | 답한 시점의 등록 매물 수 |

권한: 본인 행만 쓰고 읽는다. 운영진은 전부 읽는다.

## 7. 유료 의향 설문

- 질문: **"정식 출시 후 유료가 되어도 계속 쓰시겠습니까?"** (사업계획서의 문장 그대로)
- 보이는 곳: 중개사 대시보드. 매물을 1건 이상 등록한 중개사에게만 — 써 보지 않은 사람의 답은 의미가 없다.
- `yes`·`depends` 면 월 요금 구간을 묻는다: 1만원 미만 / 1만~3만원 / 3만~5만원 / 5만~10만원 / 10만원 이상.
- 답한 뒤에는 요약과 "답변 수정"만 보인다.

요금 구간은 `src/utils/pilotMetrics.js` 의 상수다. **파일럿을 시작하기 전에 중개사 인터뷰 결과에 맞춰 고친다**
(DB 의 check 제약도 같이 — 구간을 바꾸면 마이그레이션이 필요하다).

## 9. 로컬 데모 모드

Supabase 없이도 같은 화면이 동작한다. 합계는 `localStorage`(`geupmae:stats`), 설문은 `geupmae:pricing-intents` 에 둔다.
두 함수는 `dataClient.rpc` 가 같은 규칙으로 흉내 낸다.

## 10. 검증 기준

1. 순수 로직 단위 테스트: 셀지 말지 판단, 하루 1회 중복 제거, 한국 시간 날짜, 전환율, 요약, 설문 검증, CSV.
2. 로컬 데모: 상세를 열면 조회 1 · 새로고침해도 1 · 전화 버튼을 누르면 문의 1 · 운영진으로 열면 그대로 · 담당 중개사로 열면 그대로.
3. 로컬 데모: 중개사 설문 저장·수정, 관리자 패널의 숫자가 위와 일치, CSV 내용.
4. 라이브 DB: 마이그레이션 적용 후 공개 키로 함수를 직접 호출 — 있는 매물은 세고, 없는 매물·모르는 종류는 세지 않는다. 비로그인으로 표를 직접 읽거나 쓸 수 없다. 확인용 행은 지운다.
5. 실제 계정으로 화면을 눌러 보는 확인은 `docs/DESKTOP_TODO.md` H 에 추가.

## 11. 한계

- **버튼을 누른 것 ≠ 통화한 것.** 데스크톱에서 전화 버튼을 누르면 통화로 이어지지 않는 경우가 많다.
  실제 문의 건수는 파일럿 중개사에게 직접 물어 대조한다.
- 중복 제거는 브라우저 단위다. 저장소를 지우거나 다른 기기로 보면 다시 센다.
- 집계 함수는 누구나 부를 수 있다. 마음먹으면 숫자를 부풀릴 수 있다 — 파일럿 규모에서는 이상치로 드러나고,
  일별 합계라 어느 날 튀었는지 보인다. 정식 출시 전에 속도 제한을 검토한다.
- 로봇 판별은 User-Agent 기준이라 완전하지 않다.
- 수집 매물은 Supabase 매물 테이블에 복제본이 있어야 조회가 세어진다(번들만 갱신하고 적재를 빼먹으면 누락).
