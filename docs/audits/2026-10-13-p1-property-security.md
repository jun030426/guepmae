## 2026-10-15 적용 기록

- 기존 매물 0건을 확인하고 정책·함수 정의를 로컬 비공개 백업에 보존했다. 새 `secure_property_writes` 마이그레이션만 적용했다.
- `property-write` v1, `inspection-report` v3 배포 완료. 두 함수의 JWT 검증은 활성화했다. AI 비밀키를 변경하지 않았다.
- 기존 3D 파일 버킷에도 사진·360과 같은 소유권/승인 보호를 적용했다.
- Node 회귀 테스트 **205개**, Vite 운영 빌드, 두 Edge 진입점의 Deno 타입 검사 통과.
- 실제 Supabase Auth·PostgREST·Storage·Edge를 통한 **14개 보안 시나리오 통과**. 등록→작성자/운영진만 조회→운영 승인→공개→수정→비공개, 오래된 승인 거부, 권한/가격 위조 차단, 직접 쓰기/RPC 차단, 사진 보호, 정지 즉시 적용, 실제 실거래 기준가 일치 등을 검증했다.
- 테스트 계정 5개와 합성 매물·이미지는 검사 후 삭제했다. 실사용자의 프로필·매물·실거래 자료는 수정하지 않았다.
- 재검증 스크립트는 `scripts/verify-property-security.mjs`. 반드시 비공개 환경 파일을 사용하고 `--run`을 명시해야 하며, 대상 프로젝트를 고정하고 생성한 테스트 자료만 정리한다.
- Supabase 사후 점검에서 새 위험 항목은 발견되지 않았다. 기존 함수 권한/검색 경로, public의 pg_trgm, 유출 비밀번호 차단 미설정 등 별도 검토 항목은 남아 있다. [공식 권한 점검 기준](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable).

## 바뀐 동작

- 등록·수정·승인은 `property-write` Edge Function을 거친다. DB에서 브라우저의 직접 INSERT/UPDATE 권한을 회수한다.
- 서버가 Auth 사용자와 현재 프로필의 역할·정지 상태를 확인한다. 사용자 입력의 승인 상태, 기준가, 할인율, 가격 근거, 담당자 신원, 등록자 ID를 받지 않는다.
- 기준가·할인율은 서버 DB의 단지 실거래/중앙값으로 매번 계산한다. 브라우저 미리보기·기존 파이프라인과 같은 순수 함수를 사용한다. 데이터 조회 오류는 저장 실패로 처리하고, 데이터가 실제로 없으면 판정 보류(null)로 저장한다.
- 등록자 `created_by`는 Auth UUID로 고정한다. 이메일 변경이나 매물 JSON 변조로 소유권을 넘길 수 없다. 과거 `agent.email`은 신뢰할 수 없어 기존 행에 자동 소유권을 부여하지 않는다.
- 승인 대기 행은 작성자와 운영진이 조회한다. 다른 중개사·일반회원·익명 사용자에게는 승인된 행만 보인다.
- 내용을 수정하면 다시 승인 대기로 전환하고 승인일을 비운다. 운영진이 승인하는 사이 매물이 바뀌면 `revision` 비교로 승인을 거부한다.
- DB 저장 함수가 행을 잠근 상태에서 역할·정지·소유권을 재검사한다. 가격 조회 도중 정지된 계정도 저장할 수 없다.
- 사진/360 업로드 경로를 `사용자UUID/매물ID/파일명`으로 바꾼다. 다른 사용자의 파일 변경을 막고, 중개사가 승인된 매물의 사진 파일을 직접 덮어쓰거나 삭제하지 못하게 한다. 수정용 새 파일 업로드는 허용한다.
- AI 점검 리포트의 소유권 검사도 UUID와 현재 정지 상태를 사용한다.
- 하이브리드 모드 매물 조회는 DB/RLS를 직접 사용한다. 승인 취소·삭제 후 과거 번들 매물이 다시 등장하지 않는다. 로그인 전환 시 이전 사용자의 조회 결과를 버린다. 조회 실패와 매물 없음은 다르게 표시한다.
- 등록일을 최근 거래일이나 승인일로 저장하지 않는다.

## 계정 접근 확인

2026-10-13 현재 연결된 Supabase 도구로 급매 프로젝트 `oormfipegcfbhvctikfl`을 조회했으나 권한 거부가 반환됐다. 이 프로젝트를 관리할 수 있는 Supabase 계정/조직으로 연결해야 운영 스키마 확인, 마이그레이션, 함수 배포, 실제 Auth 검증을 마칠 수 있다. 다른 프로젝트는 수정하지 않았다.

프런트엔드는 기존 GitHub→Vercel 배포 연결을 사용하므로 별도의 Vercel 계정 변경은 필수가 아니다. 다만 현재 연결로 해당 Vercel 프로젝트 관리 권한은 확인되지 않았으며, 운영 로그·환경 설정을 직접 확인하려면 해당 계정 접근이 필요하다.

## 운영 적용 순서

프런트엔드만 먼저 배포하면 새 저장 함수가 없어 등록·수정·승인이 실패한다. 아래 순서를 유지한다.

1. **대상 확인 및 사전 점검.** Supabase 프로젝트 ref가 위 값인지 확인하고, 현재 `properties` 컬럼·정책·함수·Storage 정책과 마이그레이션 이력을 확인한다. 기존 정책 정의와 데이터를 복구 가능하게 보존한다. 저장소의 초기 마이그레이션 일부는 수동 적용을 전제로 했으므로 전체 이력을 무조건 push하지 않는다.
2. **마이그레이션 적용.** `supabase/migrations/20261013061805_secure_property_writes.sql`을 검토한 뒤 한 트랜잭션으로 적용한다. 이 파일은 properties의 기존 정책을 모두 교체한다. 수동 정책이 있다면 의도를 비교한다. 기존 행의 `created_by IS NULL`은 운영진 관리 대상으로 남긴다. 이메일만 보고 채우지 않는다. 소유권을 부여해야 한다면 별도 근거로 확인한다.
3. **서버 함수 배포.** `property-write`와 변경된 `inspection-report`를 같은 프로젝트에 배포한다. `_shared`도 함께 번들된다. JWT 검증은 켜 둔다. 표준 Supabase 환경 변수 외에 새 비밀키는 필요 없다. 기존 AI 함수의 `GEMINI_API_KEY`는 유지한다. 배포 CLI를 사용할 때 해당 버전의 `functions deploy --help`로 옵션을 먼저 확인한다.
4. **운영과 분리한 테스트 계정/데이터로 검증.** 중개사 A/B, 운영진, 정지 계정, 비로그인 상태에서 아래 시나리오를 확인한다. 실제 Auth JWT·PostgREST·Storage·Edge 게이트웨이 확인은 아직 남아 있다. 현재 운영 매물이 빈 상태라는 의도를 유지한다.
5. **프런트엔드 배포.** 위 검증 후 GitHub 변경을 반영하고 Vercel 배포를 확인한다. 등록→내 매물→승인→공개 조회→수정→승인 대기 흐름을 확인한다. 카카오는 배포 도메인에서 확인하고, 로컬 지도는 기존대로 OSM을 사용한다.

DB 적용부터 새 프런트엔드 배포까지 구버전 브라우저의 저장은 차단된다. 이 전환 구간은 짧게 잡고, 오류가 나더라도 취약했던 쓰기 권한을 다시 열지 않는다.

## 검증

- `scripts/dev.ps1 test`: 기존 182개 + 새 PostgreSQL/HTTP 보안 시나리오 11개 = **193개 통과**.
- PGlite의 실제 PostgreSQL 엔진으로 새 마이그레이션, 권한, RLS, 저장 함수를 실행했다. Supabase Auth/Storage의 최소 스키마는 테스트용 fixture이며 운영 전체 환경을 대체하지 않는다.
- 익명/일반회원/다른 중개사의 대기 매물 조회 차단, 작성자/운영진 조회 허용.
- 모든 브라우저 역할의 직접 INSERT/UPDATE 및 서버 전용 RPC 호출 차단.
- 승인·소유권·담당자·가격 근거 변조, 음수/잘못된 가격, 정지 계정 차단.
- 운영 승인→공개→수정→비공개, 오래된 승인 요청 거부, 저장 직전 정지 및 매물 변경 재검사.
- 이메일 변경 후 소유권 유지, 기존 이메일로 소유권 탈취 차단.
- 가격/층 변경과 승인 시 실거래 기준가 재계산, 근거 스냅샷 일치, DB 오류 시 미저장.
- 타인 사진 변경과 승인 사진 덮어쓰기/삭제 차단, 공개 사진 읽기·새 수정 사진 업로드 허용.
- HTTP 인증 실패·잘못된 JSON·과대 요청 거부 및 정상 등록.
- `deno check`로 두 Edge Function 진입점 검증 통과.
- Vite 운영 빌드 성공. 기존 큰 번들 경고는 P2 항목으로 남아 있다.
